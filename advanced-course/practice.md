# Как пройти цикл в роли архитектора

В уроках ты передаёшь системе задачу целиком. Ты не обязан вручную назначать каждой роли следующую реплику, писать каждый тест и повторять действия агента в интерфейсе. Твоя работа — создать достаточную постановку, разрешить содержательные вопросы и принять результат.

Сначала прочитай [общую схему фабрики](factory.md). Точные бизнес-правила и данные находятся рядом с каждым уроком.

## Подготовь вход

Передай ведущему агенту цель, точный учебный проект, правила, критерии результата и полномочия. Укажи, что уже есть, что нельзя менять и какие наблюдения нужны для приёмки. Пути должны существовать; реальные метаданные агент исследует по исходникам.

Учебный 1С-проект и репозиторий статей — разные каталоги. В рабочую область ученика не входят авторские ответы, исправленная версия дефекта и история их подготовки. Установка инструментов разобрана во [вводном курсе](../course/getting-started/lesson.md), стартовые состояния — в [lab.md](lab.md).

До запуска автор/оператор стенда подтверждает версии, чистую исходную точку Git, настройки проекта, провайдеров ревью, точный учебный контур, разрешённые действия и восстановление. Эта подготовка делает дальнейшее вмешательство человека редким. Её нельзя скрыть за обещанием «один запрос решает всё».

## После поручения

1. Ведущий агент организует подготовку требований, критериев и независимых тестов по установленному контракту `1c-task`. Защищённые тесты готовы до dispatch реализации; их подготовка вне `Run` объяснена в [factory.md](factory.md).
2. Контроллер регистрирует задачу и ведёт её через обязательные стадии.
3. Система обрабатывает замечания в пределах доступного цикла; содержательную неопределённость возвращает архитектору.
4. После проверок агенты собирают пакет сдачи с точной ревизией и ограничениями.
5. Ты оцениваешь продукт и существенное доказательство, принимаешь результат или возвращаешь конкретное замечание.

В первом уроке предусмотрено чтение финальной спецификации перед разрешением реализации. Это обучающая точка решения, а не обязательная ручная подпись после каждого будущего запуска. Во втором при готовой постановке можно пройти сразу весь разрешённый цикл.

## Когда вмешиваться

| Ситуация | Действие архитектора |
|---|---|
| Не определено поведение при частичном успехе или изменении истории | Выбрать бизнес-правило и вернуть его доверенным обновлением задачи |
| Новый запрос меняет согласованные условия | Указать изменение и границы; поручить обновление спеки, анализ влияния и регрессию |
| Агент предъявил недостаточное доказательство | Назвать недостающее наблюдение и вернуть вопрос в процесс |
| Недоступен обязательный reviewer или runner | Установить конкретный blocker и способ устранения; не подменять результат одобрением |
| Неясно, завершилась ли запись | Потребовать установить фактическое состояние до повтора |
| Все условия определены и проверки доступны | Дать процессу продолжиться в разрешённых границах |

Повторять согласование каждого обратимого исправления не нужно. Новая база, изменение бизнес-смысла или публикация не следуют автоматически из разрешения написать код.

## Как читать результат

Агенты подготавливают связь «требование → решение → изменённый код → достаточная проверка → фактический результат». Для одного значимого случая пройди эту цепочку сам. При расхождении задай конкретный вопрос о недостающем звене.

Ожидаемые числа берутся из независимых условий. Поручить агенту пересчитать их можно; получить эталон запуском проверяемого алгоритма — недостаточно. Выбор независимого примера не превращает тебя в ручного исполнителя всего набора тестов.

| Свидетельство | Что оно доказывает |
|---|---|
| Ручная арифметика | Согласованность ожидаемых чисел |
| Проверка исходников | Проверенные свойства кода и структуры |
| Code review и coverage | Качество реализации и достаточность предусмотренных наблюдений |
| Сборка и тестовый отчёт | Фактически выполненные действия на указанной ревизии |
| Два пересекающихся сеанса | Конкурентное поведение конкретного опыта |
| Receipt контроллера | Принятие точной задачи по её текущим обязательным gates |

Отчёт о проверке и рецепт её будущего запуска — разные артефакты. ACCEPT, REJECT и BLOCKED относятся к конкретному требованию и уровню доказательства. Недоступная обязательная проверка не исчезает из задания.

## Как передавать продолжение

Передачу делают после завершённого этапа, когда состояние операций установлено. Ведущий собирает краткий контекст: ID задачи, принятая спека, текущая ревизия, результаты, открытый вопрос и следующий допустимый шаг. Полная переписка не нужна.

Новый ведущий сверяет контекст с `Status`, журналом и исходниками. Управляемая задача сохраняет идентичность. Если прежний исполнитель ещё работает, второй writer не запускается. При неопределённом эффекте сначала устанавливается состояние.

Файлы результата, ссылки на реальные отчёты и объяснение решения — достаточный материал для приёмки. Не составляй дополнительную отчётность ради демонстрации «фабрики».
