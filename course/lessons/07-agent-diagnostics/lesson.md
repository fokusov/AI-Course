# Урок 7. Диагностика с агентом: от симптома к доказанной причине

> Рабочая ситуация: после очередного изменения расширения расход товара по-прежнему создаётся на основании заказа, типовое заполнение работает, поле `Заказ` видно, но ссылка остаётся пустой. Ошибки пользователю не показаны, а статические проверки зелёные.

## Что получится в конце

Главный артефакт урока:

```text
C:\AI-Course-Work\Evidence\Lesson-7\diagnosis.md
```

Он содержит:

- точное описание воспроизводимого симптома;
- сохранённое исходное состояние;
- дерево конкурирующих гипотез;
- последовательность экспериментов от дешёвых к дорогим;
- факты, которые подтвердили или опровергли каждую гипотезу;
- доказанную причину;
- preview минимального исправления;
- план регрессионной проверки и восстановления;
- одно первоначальное предположение человека или агента, которое оказалось неверным.

## Два навыка урока

### AI-навык

Использовать агента для расширения и сужения пространства гипотез. Не просить «починить», пока причина не доказана; давать новые улики порциями и заставлять агента пересматривать выводы.

### 1С-навык

Различать слои отказа в расширении: загруженная версия, активность и безопасный режим, вызов перехватчика, фактический тип `ДанныеЗаполнения`, выполнение условия и последующее изменение значения.

## Сколько времени понадобится

- самостоятельно: 2–3 часа;
- с преподавателем: около 135 минут;
- ускоренный маршрут опытного разработчика: 90 минут, но с полным `diagnosis.md`.

## Что понадобится

- завершённый [урок 6](../06-agent-code-review/lesson.md);
- принятая первая итерация `AI_Course_Lab`;
- Codex и Unica;
- спецификация, `Evidence\Lesson-5\03-runtime-pilot.md` и `Evidence\Lesson-5\04-acceptance.md` предыдущей задачи;
- четыре файла диагностического досье, которые открываются строго по порядку;
- чистый Git-baseline.

Основной маршрут урока работает по сохранённым свидетельствам и не изменяет информационную базу. Файл `references/04-change-diff.md` — часть учебного досье: он изображает уже зафиксированное изменение, которое породило симптом после принятой итерации урока 6. Этот diff не обязан присутствовать в твоей рабочей копии. Преподаватель может отдельно показать живое воспроизведение только на восстановимом учебном контуре.

## Итоговая схема

```text
SYMPTOM
  → PRESERVE
  → HYPOTHESES
  → CHEAP EXPERIMENT
  → OBSERVATION
  → NARROW / REVISE
  → ROOT CAUSE
  → MINIMAL FIX PREVIEW
  → VERIFICATION PLAN
  → ACCEPT / REJECT / BLOCKED
```

Это не новый процесс вместо `RESEARCH → SPEC → IMPLEMENT → VERIFY`. Это увеличенное изображение исследовательской части, когда неизвестно, где именно находится дефект.

## 1. Симптом не равен причине

Фраза «не заполняется заказ» описывает наблюдение, но не объясняет его. Одному симптому соответствуют разные причины:

- в базе осталась старая версия расширения;
- расширение неактивно или его обработчики ограничены безопасным режимом;
- перехватчик не вызывается;
- обработчик вызывается с другим типом данных;
- условие внутри обработчика ложно;
- ссылка заполняется, но позже перезаписывается;
- пользователь воспроизводит другой сценарий;
- исходники, которые читает агент, не соответствуют загруженному расширению.

Если сразу выбрать одну причину, все последующие наблюдения легко начать трактовать в её пользу. Поэтому диагностика хранит несколько конкурирующих гипотез и заранее записывает, какое наблюдение отличит их друг от друга.

## 2. Правило сохранения состояния

До первого эксперимента не меняй код и настройки базы.

Сначала зафиксируй:

```powershell
git status --short
git rev-parse --short HEAD
git diff -- src/extensions/AI_Course_Lab
```

В основном маршруте ожидается, что последний вызов ничего не выведет: он подтверждает чистоту твоей рабочей копии перед исследованием. Позже ты откроешь сохранённый `04-change-diff.md` как улику из сценария, а не как результат этой команды. Если локальный diff всё же есть, сохрани его отдельно и не продолжай, пока не установишь его происхождение.

В `diagnosis.md` запиши:

```markdown
## Исходное состояние

- время наблюдения:
- версия платформы:
- учебная база:
- активное расширение и его версия:
- commit исходников:
- локальный diff:
- способ восстановления:
```

Если commit, загруженный CFE и состояние базы не связаны доказательством, так и напиши. Не называй исходники причиной поведения базы только потому, что они лежат рядом на диске.

## 3. Получаем только симптом

Открой [улику 1 — карточку симптома](references/01-symptom.md). Следующие файлы пока не читай.

Перепиши симптом в форме:

```text
ДАНО:
КОГДА:
НАБЛЮДАЕМ:
ОЖИДАЕМ:
ПОВТОРЯЕМОСТЬ:
НЕ ПРОВЕРЕНО:
```

Плохое описание:

> Расширение сломалось, заказ не работает.

Хорошее описание не содержит предполагаемой причины и позволяет другому разработчику повторить действие.

## 4. Строим дерево гипотез до обращения к агенту

Запиши минимум пять гипотез. Для каждой укажи предсказание и самый дешёвый отличающий эксперимент.

| ID | Гипотеза | Что должно наблюдаться, если она верна | Дешёвый эксперимент | Риск эксперимента |
|---|---|---|---|---|
| H1 | В базе старая сборка | Хэш или версия не совпадает с ожидаемой | Сверить журнал загрузки и артефакт | Нет мутации |
| H2 | Ограничение выполнения расширения | Не выполняются и другие обработчики расширения | Проверить активность и уже известный эффект формы | Read-only |
| H3 | Не вызывается перехватчик | Нет входа в `AI_ОбработкаЗаполнения` | Трассировка или точка останова | Требует runtime-наблюдения |
| H4 | Условие не соответствует фактическому типу | Вход есть, присваивания нет | Зафиксировать `ТипЗнч(ДанныеЗаполнения)` | Требует runtime-наблюдения |
| H5 | Значение перезаписывается позже | Сразу после обработчика ссылка заполнена, после завершения — пуста | Два наблюдения в разных точках | Дороже H3/H4 |

Добавь хотя бы одну собственную гипотезу. Не включай «платформа работает неправильно», пока не сформулировано конкретное проверяемое предсказание.

## 5. Просим агента не исправлять, а спроектировать диагностику

Передай Codex только карточку симптома и своё дерево:

```text
Помоги спланировать диагностику дефекта расширения AI_Course_Lab.

Сейчас работай только на чтение. Не изменяй файлы и базу, не запускай 1С,
не предлагай исправление до доказательства причины.

Используй при необходимости $unica:source-access, $unica:code-search,
$unica:object-events и $unica:code-diagnostics для проверки текущих исходников.

Вот точный симптом и моё дерево гипотез: <вставь содержимое>.

1. Добавь пропущенные гипотезы, но не удаляй мои.
2. Для каждой укажи наблюдение, которое отличит её от соседних.
3. Расположи эксперименты по стоимости, риску и информативности.
4. Назови первый эксперимент, после которого нужно остановиться и пересмотреть
   дерево.
5. Раздели факты из проекта и предположения о runtime.

Не выбирай корневую причину только по сходству с прошлым сбоем безопасного
режима. После плана остановись.
```

Агент полезен здесь широтой поиска, но подвержен тем же якорям. Упоминание прошлого сбоя может заставить его повторить знакомый диагноз без новых доказательств.

## 6. Открываем улики по одной

После каждой улики обновляй таблицу:

| Гипотеза | До улики | Новое наблюдение | После улики | Почему |
|---|---|---|---|---|
| H1 | вероятна |  |  |  |

Допустимые статусы:

- `ACTIVE` — пока совместима с фактами;
- `WEAKENED` — возможна, но часть предсказаний не совпала;
- `REJECTED` — противоречит наблюдению;
- `CONFIRMED` — есть отличающее доказательство причины.

### Улика 2. Среда и статические проверки

Открой [улику 2](references/02-environment-and-static.md). Не переходи дальше, пока не ответишь:

1. Какие гипотезы она опровергает?
2. Какие только ослабляет?
3. Почему зелёная статика не подтверждает корректность условия по типу?
4. Какой следующий эксперимент даёт максимум информации без изменения кода?

Передай агенту новые факты и попроси обновить, а не переписать дерево с нуля.

### Улика 3. Runtime-наблюдение

Открой [улику 3](references/03-runtime-observation.md).

Теперь должны различаться как минимум три вещи:

- обработчик найден в исходниках;
- обработчик действительно вызван платформой;
- нужная ветка обработчика выполнена.

Попроси агента назвать оставшиеся гипотезы и точный участок исходника, который следует сравнить с фактическим типом. Не разрешай ему менять файл.

### Улика 4. Минимальный diff

Только после собственного вывода открой [улику 4](references/04-change-diff.md).

Проверь:

1. Объясняет ли одна изменённая строка все наблюдения?
2. Нужны ли дополнительные причины для объяснения симптома?
3. Почему код проходит синтаксическую проверку?
4. Почему прошлый диагноз про безопасный режим здесь неверен?

Корневая причина считается доказанной, когда она одновременно объясняет симптом, runtime-наблюдение и отличие от принятого baseline.

## 7. Формулируем причину без лишней уверенности

Используй шаблон:

```markdown
## Доказанная причина

В обработчике ... условие сравнивает фактическое значение типа ... с типом ... .
Обработчик вызывается, но условие ложно, поэтому присваивание ... не выполняется.

Это подтверждено:

1. ...
2. ...
3. ...

Следующие гипотезы отвергнуты:

- ... — потому что ...

Не доказано:

- ...
```

Не добавляй в причину слова «всегда», «единственная» или «точно», если досье не исключает соответствующую альтернативу.

## 8. Получаем preview минимального исправления

Только после фиксации причины попроси Codex:

```text
Причина зафиксирована в diagnosis.md. Подготовь только preview минимального
исправления в модуле объекта расширения.

Используй $unica:code-patch с dryRun. Ничего не записывай.
Не рефактори метод, не меняй форму, метаданные и основную конфигурацию.

Покажи:
- точную заменяемую строку;
- preview diff;
- почему изменение соответствует спецификации;
- какие статические и runtime-проверки понадобятся после записи.

После preview остановись.
```

Ожидаемый скоуп — одна логическая замена в условии. Если агент предлагает новый общий модуль, универсальный определитель типа или поддержку структур, он лечит задачу шире доказанной причины.

Preview не считается исправлением. В этом уроке мы сохраняем дефект как учебное свидетельство и заканчиваем планом. Применение и runtime-повтор допустимы только в отдельной восстановимой ветке преподавателя или после явного решения продолжить лабораторную работу.

## 9. Планируем проверку исправления

Минимальный набор после будущего применения:

1. Статическая диагностика изменённого модуля.
2. Структурная проверка расширения.
3. Ввод расхода на основании заказа — ссылка заполняется.
4. Ручной расход — ссылка остаётся пустой.
5. Другое поддерживаемое основание — случайная ссылка не появляется.
6. Запись и повторное открытие — ссылка сохраняется.
7. Проверка, что типовое заполнение товаров и реквизитов не изменилось.

Каждая проверка должна быть связана с причиной или риском исправления. Полный повтор всех возможных сценариев не всегда нужен, но сценарии 1–4 первой итерации затронуты непосредственно.

## 10. Контролируемая ошибка: знакомая причина

Наиболее соблазнительный быстрый ответ после урока 5:

> Снова безопасный режим. Нужно его отключить.

Почему это плохая диагностика:

- похожий симптом не делает причины одинаковыми;
- изменение настройки базы происходит раньше доказательства;
- эффект других обработчиков уже может противоречить гипотезе;
- повторное отключение защиты не объясняет ложное условие внутри вызванного метода.

Вторая крайность:

> Перепишем обработчик заполнения целиком и посмотрим, поможет ли.

Такой эксперимент смешивает несколько изменений, уничтожает исходное свидетельство и не учит нас причине. Исправление, которое случайно убрало симптом, ещё не доказывает диагноз.

## 11. Восстановление и состояние после урока

Основной маршрут не изменяет проект, поэтому ожидается:

```powershell
git status --short
git diff -- src/extensions/AI_Course_Lab
```

Если во время собственной практики ты всё же создал локальную ветку с дефектом:

1. Сохрани `diagnosis.md` вне удаляемого состояния.
2. Зафиксируй точный diff дефекта и исправления.
3. Не загружай повторно расширение только потому, что прошлый запуск непонятен.
4. Восстанови учебную базу по подтверждённому маршруту предыдущих уроков.
5. Докажи, что исходники и база вернулись к принятому baseline.

Не используй общую очистку репозитория, если не установлено происхождение всех локальных изменений.

## 12. Самостоятельная задача

Новый симптом:

> В Git виден правильный исправленный код, статические проверки проходят, но в учебной базе после запуска сохраняется прежнее поведение. Журнал загрузки в материалы не приложен.

Не называя причину заранее, составь в `diagnosis.md` отдельный план:

- минимум пять гипотез на разных слоях;
- отличающее наблюдение для каждой;
- порядок экспериментов;
- точку, после которой изменение базы допустимо или всё ещё запрещено;
- сведения, связывающие source commit, CFE, загрузку и активную версию расширения;
- статус `BLOCKED`, если необходимые свидетельства недоступны.

Задача проверяет, научился ли ты различать «исходники исправлены» и «в базе выполняется именно эта сборка».

## 13. Условия завершения

Урок завершён, если:

- симптом описан без предполагаемой причины;
- исходное состояние сохранено до экспериментов;
- построено минимум пять конкурирующих гипотез;
- у каждой есть проверяемое предсказание;
- улики открывались по порядку, а дерево обновлялось после каждой;
- знакомая причина безопасного режима отвергнута по фактам, а не по настроению;
- корневая причина объясняет всю цепочку наблюдений;
- подготовлен только preview минимального исправления;
- план проверки соответствует изменённому поведению;
- самостоятельная задача отделяет исходники, артефакт, загрузку и runtime;
- после урока нет неожиданных изменений Git и базы.

## 14. Рефлексия

Ответь:

1. Какая гипотеза первой показалась тебе очевидной?
2. Какое наблюдение сильнее всего изменило твоё мнение?
3. Агент расширил дерево или слишком рано сузил его?
4. Какой эксперимент оказался самым информативным относительно стоимости?
5. Где ты мог случайно изменить состояние до фиксации доказательств?
6. Какое правило диагностики следует сохранить для следующего проекта?

Пример полезного правила:

> До исправления дефекта зафиксировать симптом и baseline, затем для каждой активной гипотезы назвать отличающее наблюдение; не повторять прошлую причину без нового доказательства.
