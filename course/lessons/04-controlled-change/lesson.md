# Урок 4. Проводим первое контролируемое изменение

> Впервые разрешаем агенту изменить исходники. Разрешение ограничено одной спецификацией, одним расширением и заранее определённым результатом.

## Что ученик должен понять

После урока ученик должен уметь:

- начинать работу только из известного состояния Git;
- отделять план агента от разрешения на реализацию;
- задавать разрешённую область изменений;
- запрещать изменение основной конфигурации;
- читать фактический diff, а не пересказ агента;
- останавливать работу при неожиданном расширении скоупа;
- отличать изменение исходников от доказательства работы в базе;
- сохранять понятный путь отката.

Главный результат урока — минимальный проверенный на уровне исходников diff. Работу функции в информационной базе мы будем доказывать отдельно.

## Два навыка урока

### AI-навык

Давать агенту ограниченное разрешение на изменение, отделять план от реализации и принимать работу только по фактическому diff.

### 1С-навык

Создавать минимальное расширение конфигурации, не затрагивая основную поставку, и различать статическую корректность исходников и runtime-поведение базы.

## Сколько времени понадобится

- самостоятельно: 60–90 минут;
- с преподавателем: около 90 минут;
- runtime-проверка в это время не входит и выполняется в [уроке 5](../05-runtime-acceptance/lesson.md).

## Что понадобится

- контур Demo83 со статусом `READY`;
- Git-репозиторий `C:\AI-Course-Work\Demo83-Sources`;
- исходники основной конфигурации:

```text
C:\AI-Course-Work\Demo83-Sources\src\configuration
```

- подготовленный каталог будущего учебного расширения:

```text
C:\AI-Course-Work\Demo83-Sources\src\extensions\AI_Course_Lab
```

- согласованная спецификация:

```text
C:\AI-Course-Work\Demo83-Sources\openspec\changes\ai-course-order-link\spec.md
```

- отчёт review из [урока 3](../03-specification/lesson.md):

```text
C:\AI-Course-Work\Evidence\Lesson-3\02-spec-review.md
```
- рабочий baseline `01-AI-Course-ready.dt`.

То, что расширение ещё не установлено в базу, — ожидаемое состояние. Урок не начинается, если спецификация не согласована, восстановление baseline не доказано или в базе уже обнаружено неизвестное `AI_Course_Lab`.

## Что именно меняем

Первая итерация должна обеспечить только следующее поведение:

1. Создано расширение `AI_Course_Lab`, в котором у `РасходТовара` существует необязательная ссылка на `Заказ`.
2. При создании расхода на основании заказа ссылка заполняется автоматически.
3. Самостоятельный расход может существовать без заказа.
4. В проведённом расходе ссылка недоступна для изменения.
5. Основная конфигурация Demo83 не изменяется.

Мы пока не реализуем:

- автоматическое состояние заказа;
- подсчёт отгруженного количества;
- реакцию на отмену проведения;
- блокировки пересчёта;
- уведомления;
- восстановление старых связей.

Если агент пытается добавить что-либо из этого списка, он вышел за границы задачи.

## Итоговая схема урока

```text
RESEARCH: проверить Git и точки изменения
  ↓
SPEC: зафиксировать разрешённый скоуп
  ↓
IMPLEMENT: получить план, затем минимальный diff
  ↓
VERIFY: проверить план, diff и статические диагностики
  ↓
Остановиться до загрузки в базу: ACCEPT / REJECT / BLOCKED по уровню исходников
```

## Часть 1. Проверяем исходное состояние

Открой PowerShell в каталоге:

```powershell
Set-Location C:\AI-Course-Work\Demo83-Sources
```

Проверь состояние:

```powershell
git status --short
git branch --show-current
git log -1 --oneline
```

Сохрани вывод в:

```text
C:\AI-Course-Work\Evidence\Lesson-4\01-before.txt
```

### Ожидаемый результат

- `git status --short` не выводит изменённых файлов;
- текущая ветка известна;
- последний коммит соответствует подготовленному состоянию курса;
- в каталоге есть спецификация и исходники расширения;
- `src\configuration` совпадает с официальным baseline.

Если репозиторий уже содержит изменения, не удаляй их и не проси агента «привести всё в порядок». Сначала установи владельца и назначение каждого изменения. Неизвестный dirty state означает `BLOCKED`.

## Часть 2. Создаём рабочую ветку

Для упражнения создай отдельную ветку:

```powershell
git switch -c lesson-4-order-link
```

Если такая ветка уже существует, не добавляй случайный суффикс и не удаляй её автоматически. Выясни, относится ли она к предыдущей попытке, и либо продолжи осознанно, либо выбери другое понятное имя.

Ветка не заменяет `.dt` и не откатывает информационную базу. Она защищает историю исходников. Baseline защищает состояние базы. Для 1С-задачи нужны оба механизма.

## Часть 3. Фиксируем разрешения агента

До обращения к агенту запиши границы:

| Область | Разрешение |
|---|---|
| `openspec\changes\ai-course-order-link\spec.md` | читать |
| `src\configuration` | только читать |
| `src\extensions\AI_Course_Lab` | разрешено изменять после согласования плана |
| информационная база | не изменять |
| `.dt` baseline | не изменять |
| внешние подключения | не использовать |
| другие файлы репозитория | не изменять |

Сохрани таблицу в:

```text
C:\AI-Course-Work\Evidence\Lesson-4\02-scope.md
```

Скоуп — это не пожелание. Если агенту действительно понадобится другой файл, он должен остановиться и объяснить причину.

## Часть 4. Сначала просим только план

До отправки промпта запиши прогноз: какие объекты и файлы агент предложит изменить и назовёт ли он хотя бы один файл основной конфигурации. После ответа сравни прогноз с планом; неожиданное расширение скоупа — повод остановиться до реализации.

Открой новую задачу Codex Desktop в корне `Demo83-Sources`. Убедись, что Unica видит source-set основной конфигурации и учебного расширения. Передай:

```text
Нужно подготовить реализацию спецификации openspec/changes/ai-course-order-link/spec.md.

Сейчас работай только на чтение. Ничего не изменяй.

Разрешённый будущий скоуп изменений:
- src/extensions/AI_Course_Lab/**

Запрещено изменять:
- src/configuration/**;
- информационную базу;
- baseline-файлы;
- остальные файлы репозитория.

Исследуй текущие исходники конфигурации и расширения. Подготовь минимальный план:
1. как создать расширение и какие объекты нужно заимствовать или изменить;
2. какой реквизит добавить и с каким типом;
3. где заполнить ссылку при вводе на основании;
4. как сделать поле недоступным после проведения;
5. какие файлы изменятся;
6. какие статические и runtime-проверки потребуются;
7. какие возможности расширения ещё не подтверждены.

Отдельно перечисли риски и стоп-условия.
После плана остановись. Код не пиши.
```

На стадии плана Codex может применять read-only skills `$unica:cfe-diff`, `$unica:meta-info`, `$unica:form-info`, `$unica:code-search` и `$unica:source-access`. Наличие инструмента редактирования ещё не является разрешением его использовать.

Сохрани ответ:

```text
C:\AI-Course-Work\Evidence\Lesson-4\03-implementation-plan.md
```

## Часть 5. Проверяем план

План можно принять, только если он отвечает на все вопросы ниже.

### Состав изменения

- Названы конкретные объекты расширения.
- Тип реквизита — только `ДокументСсылка.Заказ`.
- `ОбоснованиеОтгрузки` не переиспользуется.
- Основная конфигурация остаётся только источником чтения.

### Точка заполнения

- Агент нашёл существующую `ОбработкаЗаполнения` расхода.
- Он учитывает только основание типа `ДокументСсылка.Заказ`.
- Существующее копирование шапки и товаров не должно сломаться или выполниться дважды.

### Форма

- Поле доступно в новом или непроведённом расходе.
- После проведения оно недоступно.
- Решение не запрещает просмотр ссылки.

### Проверка

- Статика отделена от сборки.
- Сборка отделена от загрузки в базу.
- Runtime-сценарии перечислены, но пока не выполняются.
- Есть негативный сценарий самостоятельного расхода.
- Есть проверка существующего расхода с пустой ссылкой.

### Границы

- В плане нет автоматического изменения состояния заказа.
- Не добавлены новые самостоятельные объекты метаданных.
- Не затронуты регистры и движения.
- Не предложена массовая миграция.

Если план требует изменить `src\configuration`, статус задачи — `BLOCKED`. Не расширяй разрешения автоматически.

## Часть 6. Разрешаем минимальную реализацию

После принятия плана дай отдельное разрешение:

```text
План согласован. Реализуй только первую итерацию по
openspec/changes/ai-course-order-link/spec.md.

Разрешено изменять только:
- src/extensions/AI_Course_Lab/**

Основную конфигурацию, информационную базу, baseline, спецификацию и другие
файлы не изменяй.

Требования:
- минимальный diff;
- реквизит Заказ типа ДокументСсылка.Заказ;
- заполнение только при создании РасходТовара на основании Заказа;
- сохранение существующего заполнения документа;
- поле видно всегда, но недоступно для изменения после проведения;
- никаких изменений состояния заказа;
- никаких новых независимых объектов метаданных;
- никаких операций с базой.

После изменения:
1. покажи список изменённых файлов;
2. объясни назначение каждого изменения;
3. выполни доступную статическую валидацию исходников расширения;
4. сообщи отдельно, что осталось непроверенным без сборки и runtime.

Если нужная точка расширения недоступна или требуется выход за скоуп,
остановись и задай вопрос. Не ищи обходной путь самостоятельно.
```

Для реализации Codex выбирает минимальный набор профильных skills по фактическому плану: `$unica:cfe-init` для создания расширения, затем при необходимости `$unica:cfe-borrow`, `$unica:meta-add`, `$unica:form-edit`, `$unica:code-patch`. После изменения он использует соответствующие read-only проверки, включая `$unica:cfe-validate`, `$unica:form-validate` и `$unica:code-diagnostics`. Перечень не является командой применить их все: каждый вызов должен соответствовать конкретному изменённому артефакту.

Во время работы следи не только за финальным ответом. Если интерфейс показывает операции агента, проверяй:

- какие файлы он читает;
- какие файлы собирается изменить;
- не запускает ли загрузку в базу;
- не расширяет ли задачу «для полноты».

## Часть 7. Проверяем фактический diff

После остановки агента сначала выполни:

```powershell
git status --short
git diff --stat
git diff --check
```

Затем прочитай полный diff:

```powershell
git diff -- src/extensions/AI_Course_Lab
```

И отдельно докажи отсутствие изменений основной конфигурации:

```powershell
git diff --exit-code -- src/configuration
```

### Что проверяем вручную

#### Метаданные

- Добавлен ровно один прикладной реквизит `Заказ`.
- Тип ссылки узкий и однозначный.
- Реквизит не объявлен обязательным для всех расходов.
- Нет случайных изменений UUID существующих объектов.

#### Заполнение

- Ссылка берётся из реально переданного основания.
- Обрабатывается нужный тип основания.
- Существующий алгоритм основной конфигурации не скопирован целиком без необходимости.
- Не появилось заполнение по номеру, строке или совпадению товаров.

#### Форма

- Поле отображает добавленный реквизит.
- Доступность зависит от проведённости документа.
- Доступность не подменяет серверную целостность данных.

#### Скоуп

- Изменены только ожидаемые файлы расширения.
- Нет форматирования несвязанных модулей.
- Нет отладочного вывода и закомментированного кода.
- Нет заготовок автоматического пересчёта состояния.

## Часть 8. Разбираем статические проверки

Для каждой выполненной проверки запиши:

| Проверка | Результат | Что доказывает | Чего не доказывает |
|---|---|---|---|
| Структура расширения |  | XML и состав расширения согласованы | Что расширение загрузится в конкретную базу |
| Диагностика BSL |  | Найденные статические проблемы отсутствуют или разобраны | Что обработчик вызовется в runtime |
| `git diff --check` |  | В diff нет части механических дефектов | Корректность бизнес-поведения |
| Проверка скоупа |  | Основная конфигурация не изменена | Работу формы и заполнения |

Сохрани таблицу:

```text
C:\AI-Course-Work\Evidence\Lesson-4\04-static-checks.md
```

Зелёная статика означает только то, что проверили статические инструменты. Она не доказывает, что расширение собирается, загружается и выполняет требование.

## Часть 9. Стоп-точка перед базой

На этом урок заканчивается.

Не нужно:

- загружать расширение в базу;
- обновлять конфигурацию базы;
- открывать форму расхода для «быстрой проверки»;
- проводить документы;
- принимать изменение как готовое.

Почему мы останавливаемся: изменение исходников уже произошло, а следующий переход меняет внешнее состояние — учебную информационную базу. Для него нужны отдельный preflight, точный порядок операций и фиксация свидетельств.

## Контролируемая ошибка: правдоподобный лишний diff

Представь, что вместе с расширением агент изменил модуль объекта `Документ.РасходТовара` в основной конфигурации и объяснил это тем, что «так надёжнее заполнить ссылку». Не принимай объяснение на доверии. Зафиксируй нарушение скоупа, верни статус `REJECT` и сформулируй новое ограниченное задание: сохранить основную конфигурацию неизменной и доказать точку расширения либо вернуть `BLOCKED`.

Ошибка здесь не обязательно в синтаксисе кода. Она в том, что агент выбрал более широкий и труднее обновляемый путь без разрешения.

## Что делать при выходе агента за скоуп

Если агент изменил неожиданный файл:

1. Останови дальнейшие действия.
2. Сохрани `git status --short` и diff как свидетельство.
3. Определи, относится ли изменение к текущей задаче.
4. Не удаляй все изменения репозитория общей командой.
5. Попроси агента объяснить необходимость файла без новых прав на изменение.
6. Отклони лишнюю часть или пересмотри спецификацию отдельным решением.

Неожиданный diff — это не автоматически плохой код. Это нарушение согласованного процесса, которое должно быть разобрано до продолжения.

## Условия завершения урока

Урок завершён, если:

- исходное состояние Git сохранено;
- работа идёт в отдельной понятной ветке;
- разрешённый скоуп записан;
- план агента проверен до реализации;
- изменено только учебное расширение;
- основная конфигурация не изменилась;
- полный diff прочитан человеком;
- статические проверки выполнены и интерпретированы;
- runtime остаётся явно непроверенным;
- информационная база после урока не изменялась.

Если исходники выглядят правдоподобно, но их состав или скоуп не подтверждён, результат остаётся `BLOCKED`.

## Самостоятельная задача

Попроси агента провести повторное read-only review собственного diff от лица сопровождающего типовую конфигурацию. Он должен перечислить каждый изменённый объект, цель изменения и доказательство того, что основная конфигурация не затронута. Сопоставь ответ с `git diff --name-only`; расхождение означает `BLOCKED`.

## Рефлексия

Ответь письменно:

1. Что оказалось полезнее для контроля: хороший промпт или заранее записанный скоуп — и почему?
2. Какое изменение выглядело разумным, но не было разрешено спецификацией?
3. Как ты отличил статически правдоподобный результат от доказанного runtime-поведения?
4. В какой момент откат ещё дешёв и почему урок останавливается именно там?

## Что будет дальше

В следующем уроке мы проведём изменение через следующие слои доказательств:

```text
исходники
  → статическая валидация
  → сборка расширения
  → загрузка в учебную базу
  → запуск пользовательских сценариев
  → решение о приёмке
```

Только после runtime-проверки станет известно, действительно ли ссылка создаётся, заполняется и ведёт себя в форме так, как требует спецификация.
