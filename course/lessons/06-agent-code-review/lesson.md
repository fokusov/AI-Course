# Урок 6. Ревью кода агента: находим опасное в правдоподобном diff

> Рабочая ситуация: первая итерация связи `РасходТовара → Заказ` уже принята. Агент предлагает три небольших «улучшения». Все выглядят разумно, но ни одно нельзя принимать по красоте кода или объяснения.

## Что получится в конце

Главный артефакт урока:

```text
C:\AI-Course-Work\Evidence\Lesson-6\review.md
```

В нём будут:

- решение по каждому из трёх diff: `ACCEPT`, `REJECT` или `BLOCKED`;
- конкретные замечания с путём, фрагментом и нарушенным требованием;
- разделение дефектов кода, бизнес-рисков, выхода за скоуп и пробелов проверки;
- минимум одно заключение агента, которое ученик перепроверил и уточнил или отклонил;
- перечень проверок, которые потребовались бы после исправления.

## Два навыка урока

### AI-навык

Использовать агента как помощника ревьюера, не передавая ему право выносить итоговое решение. Требовать доказательства, отделять найденный дефект от предположения и замечать, когда агент обсуждает стиль вместо поведения.

### 1С-навык

Ревью расширения 1С по слоям: обработчик объекта, события формы, жизненный цикл документа, побочные записи, частичные отгрузки и границы между статической проверкой и runtime-поведением.

## Сколько времени понадобится

- самостоятельно: 90–120 минут;
- с преподавателем: около 90 минут;
- ускоренный маршрут опытного ревьюера: 60 минут, но с тем же итоговым `review.md`.

## Что понадобится

- завершённый [урок 5](../05-runtime-acceptance/lesson.md) со статусом `ACCEPT`;
- чистый Git-baseline `Demo83-Sources`;
- расширение `AI_Course_Lab` из принятой первой итерации;
- спецификация `openspec/changes/ai-course-order-link/spec.md`;
- [пакет трёх diff для ревью](references/review-pack.md);
- Codex с Unica;
- каталог `C:\AI-Course-Work\Evidence\Lesson-6`.

В этом уроке ничего не загружается в информационную базу. Патчи не применяются к исходникам: мы учимся принимать решение до изменения проекта.

## Итоговая схема

```text
контракт и baseline
  → собственный прогноз
  → чтение diff
  → гипотезы о последствиях
  → независимое ревью Codex + Unica
  → проверка доказательств
  → ACCEPT / REJECT / BLOCKED
  → план минимальной проверки
```

## 1. Почему «код выглядит нормально» ничего не доказывает

Ревью агентного кода отличается не новым набором правил, а скоростью появления правдоподобных изменений. Агент способен за минуты произвести больше кода, чем разработчик успевает внимательно прочитать. Если проверять только синтаксис и стиль, преимущество превращается в растущий долг.

Хорошее ревью отвечает не на вопрос «нравится ли мне этот код», а на пять вопросов:

1. Какое наблюдаемое поведение меняется?
2. Входит ли это поведение в согласованную задачу?
3. На каких фактах и бизнес-правилах основано решение?
4. Какие побочные эффекты и граничные сценарии появились?
5. Каким свидетельством мы докажем результат?

Комментарий без ответа хотя бы на один из этих вопросов может быть полезной мыслью, но ещё не является основанием отклонить изменение.

## 2. Четыре класса замечаний

Используй небольшой словарь вместо десятков уровней серьёзности.

| Класс | Что означает | Пример решения |
|---|---|---|
| `BLOCKER` | Нарушено требование, целостность данных, безопасность или согласованный скоуп | Отклонить до исправления |
| `SHOULD FIX` | Решение может работать, но создаёт значимый долг или ненужный риск | Исправить сейчас либо явно принять долг |
| `QUESTION` | Для решения не хватает факта или бизнес-правила | Остановить приёмку и запросить данные |
| `NOTE` | Неблокирующее наблюдение | Не выдавать за дефект |

Отдельно от серьёзности укажи тип замечания:

- `behavior` — неверное прикладное поведение;
- `scope` — изменение не входит в итерацию;
- `platform` — неверно учтён механизм 1С;
- `verification` — код, возможно, верен, но нужное свойство не доказано;
- `maintainability` — понятность и дальнейшее сопровождение.

Не ставь `BLOCKER` только потому, что написал бы код иначе.

## 3. Проверяем исходное состояние

Из `Demo83-Sources` выполни:

```powershell
git status --short
git diff --exit-code -- src/configuration
git diff aa94e3a..HEAD -- src/extensions/AI_Course_Lab
```

Ожидается:

- нет неожиданных локальных изменений;
- основная конфигурация не отличается;
- после коммита принятого прототипа `aa94e3a` исходники расширения не менялись.

Если последнее условие не выполняется, не сравнивай учебные diff с другой реализацией. Сначала зафиксируй текущую ревизию и выясни происхождение расхождения.

Создай заготовку артефакта:

```markdown
# Ревью предложенных изменений AI_Course_Lab

## Контекст

- baseline:
- спецификация:
- проверяемая итерация:
- состояние Git:

## Кандидат A

- решение:
- замечания:
- необходимые проверки:

## Кандидат B

- решение:
- замечания:
- необходимые проверки:

## Кандидат C

- решение:
- замечания:
- необходимые проверки:

## Где я не согласился с агентом

## Итог
```

## 4. Сначала делаем собственный прогноз

Открой [пакет diff](references/review-pack.md), но пока не передавай его агенту.

На каждый кандидат выдели не более десяти минут и запиши:

1. Что фактически изменяется?
2. Какую проблему автор, вероятно, пытался решить?
3. Какое требование или сценарий нужно перечитать?
4. Что может сломаться, даже если BSL компилируется?
5. Какой первоначальный статус ты бы поставил?

Ограничение времени важно. Цель первого прохода — не доказать всё, а сформировать независимые гипотезы до того, как ответ агента станет якорем.

## 5. Даём Codex задачу именно на ревью

Открой `Demo83-Sources` в Codex. Передай ему спецификацию и содержимое трёх diff из пакета:

```text
Выполни ревью трёх предложенных diff для уже принятой первой итерации
ai-course-order-link.

Используй $unica:code-review и при необходимости read-only skills Unica для
проверки фактической структуры, событий объекта и формы. Ничего не изменяй,
не применяй патчи, не запускай 1С и не работай вне открытого проекта.

Источники истины:
1. openspec/changes/ai-course-order-link/spec.md;
2. текущее принятое расширение src/extensions/AI_Course_Lab;
3. подтверждённые сценарии из `Evidence\Lesson-5\03-runtime-pilot.md` и решение из `Evidence\Lesson-5\04-acceptance.md`.

Для каждого кандидата:
- кратко опиши фактическое изменение поведения;
- перечисли замечания как BLOCKER / SHOULD FIX / QUESTION / NOTE;
- пометь тип: behavior / scope / platform / verification / maintainability;
- для каждого замечания приведи конкретное требование и путь к исходнику;
- отдели доказанный дефект от риска, который ещё нужно проверить;
- вынеси решение ACCEPT / REJECT / BLOCKED;
- назови минимальные проверки после исправления.

Не предлагай полную реализацию и не переписывай код. Если diff выглядит
полезным, но относится к следующей итерации, оцени его по текущей спецификации,
а не по предполагаемому будущему дизайну. После отчёта остановись.
```

Почему в промпте уже перечислены источники истины: ревью без контракта быстро превращается в соревнование вкусов. Агент должен сравнивать код с задачей и доказательствами, а не с абстрактным представлением об идеальной архитектуре.

## 6. Проверяем ревью агента

Не копируй ответ целиком в `review.md`. Для каждого замечания выполни четыре проверки.

### 6.1. Указан ли наблюдаемый эффект

Слабое замечание:

> Этот код потенциально опасен и нарушает best practices.

Проверяемое замечание:

> После удаления обработчика `ПослеЗаписиНаСервере` поле не обновит доступность сразу после проведения; сценарий 5 требует результат без переоткрытия формы.

### 6.2. Есть ли опора на текущий контракт

Будущее автоматическое состояние заказа не входит в первую итерацию. Даже качественная реализация этой функции сейчас является выходом за скоуп. Это не значит, что идея плохая навсегда; для неё нужна следующая спецификация.

### 6.3. Не перепутал ли агент вероятность с фактом

Формулировка «может привести к неверной связи» требует сценария, в котором это произойдёт. Формулировка «обращение к несуществующему реквизиту» требует проверки реальных метаданных. Если доказательства нет, статус замечания — `QUESTION` или риск проверки, а не доказанный `BLOCKER`.

### 6.4. Достаточна ли предложенная проверка

- статическая диагностика способна найти часть ошибок BSL;
- структурная проверка формы способна подтвердить наличие обработчика и элемента;
- только runtime/UI-сценарий докажет изменение доступности поля без переоткрытия;
- только сценарии нескольких и отменённых расходов способны подтвердить будущий расчёт состояния заказа.

## 7. Собираем итоговый отчёт

Каждое существенное замечание оформи одинаково:

```markdown
### [BLOCKER][behavior] Короткое название

**Где:** кандидат B, модуль формы, удаление `AI_ПослеЗаписиНаСервере`.

**Что меняется:** после записи форма больше не пересчитывает доступность поля.

**Почему это проблема:** нарушается сценарий 5 принятой спецификации — поле
должно стать недоступным сразу после проведения без переоткрытия.

**Доказательство:** путь к текущему обработчику и ссылка на критерий приёмки.

**Решение:** вернуть обновление после записи либо предложить другой доказуемый
механизм с тем же runtime-поведением.

**Проверка после исправления:** повторить сценарии проведения и отмены проведения
без закрытия формы.
```

Для каждого кандидата вынеси одно итоговое решение:

- `ACCEPT` — замечаний, препятствующих текущей итерации, нет;
- `REJECT` — есть доказанный блокирующий дефект или выход за скоуп;
- `BLOCKED` — решение зависит от отсутствующего требования или проверки.

Статус `BLOCKED` не означает «на всякий случай принять». До получения доказательства изменение остаётся непринятым.

## 8. Контролируемая ошибка: два плохих ревью

Сравни свой отчёт с двумя крайностями.

### Ревью-пересказ

```text
Код аккуратный, названия понятные. Явных ошибок не вижу. Можно принимать.
```

Оно ничего не говорит о поведении, требованиях и проверке.

### Ревью-переписывание

```text
Я бы вынес всё в общий модуль, добавил регистр, фоновые задания и универсальный
механизм расчёта состояния. Текущий подход недостаточно расширяемый.
```

Оно заменяет проверку текущей итерации новым проектированием и само расширяет скоуп.

Попроси Codex классифицировать собственный ответ: где он действительно проверял требования, а где предлагал альтернативный дизайн. Если предложение не нужно для решения текущего замечания, не включай его в обязательные исправления.

## 9. Самостоятельная задача

Проведи ещё одно ревью без подготовленного дефекта:

```powershell
git show --stat aa94e3a
git show aa94e3a -- src/extensions/AI_Course_Lab
```

Выбери один участок фактически принятого diff и ответь:

1. Какое требование он реализует?
2. Какой риск остаётся даже после семи пройденных сценариев?
3. Достаточно ли этого риска для изменения решения `ACCEPT`?
4. Какое самое дешёвое дополнительное доказательство уменьшит неопределённость?

Добавь вывод в раздел `Дополнительное наблюдение` своего `review.md`. Допустим честный результат «нового блокирующего дефекта не найдено», если он подкреплён просмотренными доказательствами.

## 10. Условия завершения

Урок завершён, если:

- патчи не применялись и исходники не изменялись;
- перед ответом агента зафиксирован собственный прогноз;
- каждый кандидат получил отдельное решение;
- каждое блокирующее замечание связано с требованием или подтверждённым механизмом 1С;
- риски без доказательств не выданы за факты;
- для исправлений названы проверки подходящего уровня;
- зафиксировано минимум одно уточнение или отклонение вывода агента;
- выполнено самостоятельное ревью части реального принятого commit;
- `git status --short` после урока не показывает неожиданных изменений.

## 11. Рефлексия

Ответь в конце `review.md`:

1. Какое замечание ты нашёл раньше агента?
2. Где агент помог увидеть связь между файлами или событиями?
3. Где его уверенная формулировка оказалась сильнее доказательств?
4. Какое замечание выглядело вкусовым, пока ты не связал его с поведением?
5. Сколько времени заняло ревью относительно написания такого diff вручную?
6. Какое правило стоит добавить в будущий `AGENTS.md` после этого опыта?

Подходящее правило должно быть конкретным. Например:

> При ревью изменения 1С каждое блокирующее замечание связывать с критерием приёмки, подтверждённым механизмом платформы или наблюдаемым регрессионным сценарием.
