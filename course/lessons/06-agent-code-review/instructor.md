# Материалы преподавателя

> Внутренний материал курса. Не включать в публичную сборку сайта.

## Главная педагогическая задача

Переключить участника с оценки «код выглядит профессионально» на проверку «какое поведение изменилось, входит ли оно в контракт и чем это будет доказано».

Ученик не обязан найти все формулировки из ключа. Он должен доказательно увидеть основную проблему каждого кандидата и не передать агенту финальное решение.

## Подготовка преподавателя

До занятия:

1. Проверить, что commit `aa94e3a` доступен в учебном репозитории.
2. Перечитать спецификацию и семь runtime-сценариев.
3. Проверить, что три diff в `references/review-pack.md` совпадают с принятой реализацией.
4. Открыть свежую задачу Codex с Unica и один раз прогнать prompt ревью только на чтение.
5. Подготовить экран с фактическими обработчиками объекта и формы.
6. Не публиковать участникам ключ разбора до их собственного прогноза.

## Очный сценарий на 90 минут

### 0–10 минут. Что вообще проверяет ревью

Показать один красивый фрагмент BSL без контекста и спросить, можно ли его принять. Собрать критерии группы, затем разложить их на поведение, скоуп, платформу и доказательства.

### 10–25 минут. Самостоятельный первый проход

Участники читают три diff без агента. На каждый фиксируют первоначальное решение и один главный риск. Не помогать с ответом, только возвращать к спецификации.

### 25–45 минут. Ревью Codex + Unica

Запустить общий prompt. Попросить участников отмечать не количество замечаний, а наличие пути, требования и проверяемого эффекта.

### 45–65 минут. Разбираем расхождения

Для каждого кандидата сравнить человеческий прогноз и ответ агента. Особое внимание уделить местам, где агент:

- обсуждает стиль вместо поведения;
- принимает «полезную» функцию вне текущего скоупа;
- выдаёт возможный риск за доказанный дефект;
- предлагает статическую проверку для UI-поведения.

### 65–80 минут. Пишем одно сильное замечание

Каждый участник оформляет одно замечание по шаблону: где, эффект, нарушенный контракт, доказательство, решение, проверка.

### 80–90 минут. Решение и рефлексия

Зафиксировать итоговые статусы, убедиться, что Git не изменился, и сформулировать одно будущее правило проекта.

## Ключ к пакету ревью

### Кандидат A — `REJECT`

Главная проблема: связь с заказом восстанавливается по номеру из произвольной структуры. Первая итерация разрешает заполнять ссылку только из типизированного основания `ДокументСсылка.Заказ`.

Существенные замечания:

- `[BLOCKER][behavior]` номер не является надёжной идентичностью ссылки;
- `[BLOCKER][scope]` добавлен альтернативный алгоритм связывания, которого нет в спецификации;
- `[QUESTION][platform]` не доказаны состав структуры, уникальность номера в нужной области и корректный контекст поиска;
- негативный сценарий ручного расхода рискует получить ложную связь.

Не делать главным замечанием стиль вложенных условий. Он вторичен.

### Кандидат B — `REJECT`

Главная проблема: удаление `ПослеЗаписиНаСервере` ломает подтверждённый сценарий изменения доступности поля сразу после проведения и отмены проведения без переоткрытия формы.

Существенные замечания:

- `[BLOCKER][behavior]` состояния формы после записи и после чтения — разные моменты жизненного цикла;
- `[BLOCKER][verification]` структурная проверка формы не докажет динамическое поведение;
- повторить нужно как минимум сценарии 5 и 6 урока 5.

Если агент утверждает, что платформа обязательно вызовет чтение после любой записи, потребовать доказательство для этой формы и этой последовательности. До него утверждение не принимается.

### Кандидат C — `REJECT`

Главная проблема: diff перескакивает к следующей крупной итерации и приравнивает один проведённый расход к полному выполнению заказа.

Существенные замечания:

- `[BLOCKER][scope]` автоматический пересчёт состояния прямо исключён из первой итерации;
- `[BLOCKER][behavior]` частичная отгрузка не означает `Выполнен`;
- `[BLOCKER][behavior]` не обработаны отмена проведения, несколько расходов, избыточная отгрузка и изменение связи;
- `[BLOCKER][platform]` запись связанного документа из проведения добавляет транзакционные, блокировочные и рекурсивные риски;
- для такого изменения нужны отдельная спецификация, исследование и набор интеграционных сценариев.

Не принимать аргумент «код маленький». Маленький diff может иметь большой blast radius.

## Допустимые варианты ответа

- Участник может поставить кандидату A `BLOCKED`, если явно запрещает приёмку до уточнения контракта. После возврата к действующей спецификации итог должен стать `REJECT`.
- Участник может выделить несколько блокеров в C или один объединяющий. Важна причинно-следственная связь, а не количество комментариев.
- Допустимо не найти нового риска в самостоятельной части, если перечислены просмотренные доказательства и границы семи сценариев.

## Типичные ошибки

- Считать количество замечаний показателем качества ревью.
- Обсуждать форматирование и имена раньше поведения.
- Предлагать готовую архитектуру следующей итерации вместо отклонения C.
- Называть любой риск блокером без сценария проявления.
- Просить агента сразу исправить патч и потерять исходное свидетельство.
- Применять diff «для проверки», хотя задача урока — решение до изменения.

## Запасной сценарий

Если Unica недоступна, Codex выполняет файловое ревью, а участники вручную открывают спецификацию, модули и runtime-отчёт. Это снижает скорость навигации, но не отменяет учебную цель.

Если Codex не находит проблем, не подсказывать ответ сразу. Попросить его для каждого diff построить таблицу «требование → изменение поведения → доказательство». Обычно противоречие становится видимым на этом шаге.

## Авторская проверка перед публикацией

- Пакет diff сверён с принятой реализацией.
- Ссылки на следующий урок появляются только после создания его каталога.
- В публичном материале нет ключа правильных ответов.
- Урок проходит полностью без изменения информационной базы.
- Очный прогон укладывается в два академических часа.
