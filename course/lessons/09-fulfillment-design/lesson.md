# Урок 9. Проектируем контроль исполнения заказов

> Рабочая ситуация: первая итерация `AI_Course_Lab` сохранила явную связь расхода с заказом. Теперь заказ может исполняться несколькими частичными отгрузками, но система пока не знает, сколько уже отгружено, сколько осталось и можно ли провести следующий расход.

В этом уроке код по-прежнему не пишется. Задача достаточно рискованна, чтобы сначала доказать факты, развести два разных состояния, выбрать модель данных и согласовать транзакционный контракт.

## Итоговая схема

```text
прежняя хотелка об автоматическом состоянии
  → повторная проверка фактов
  → разделение двух бизнес-смыслов
  → четыре архитектурных варианта
  → выбор учётного субъекта
  → движения заказа и расхода
  → контроль отрицательного остатка
  → форма + отчёт + тестовая стратегия
  → review спецификации
  → READY / BLOCKED
```

## 1. Почему мы не продолжаем старую постановку буквально

В уроке 3 большая хотелка была намеренно отложена. Тогда естественно звучало:

> После отгрузки автоматически менять `СостояниеЗаказа`.

Теперь у нас больше фактов. В Demo83 существующее `СостояниеЗаказа` содержит значения `Открыт`, `ВРаботе`, `Выполнен`, `Закрыт` и изменяется пользователем. Это жизненный цикл документа. Отгрузка отвечает на другой вопрос: сколько заказанного количества уже исполнено.

Если хранить оба смысла в одном реквизите, возникают противоречия:

- заказ может быть закрыт вручную, хотя отгружен частично;
- полностью отгруженный заказ не обязательно завершён организационно;
- отмена расхода не должна незаметно переоткрывать закрытый заказ;
- пользовательское решение и вычисляемый факт начинают перезаписывать друг друга.

В [карточке изменения скоупа](references/scope-change.md) сохрани, какое прежнее решение уточняется и почему. Мы не переписываем историю спецификации урока 3: первая итерация остаётся принятой, а новая задача получает собственную спецификацию.

## 2. Фиксируем исходное состояние без предложений

### Документ `РасходТовара`

- проведение разрешено;

- платформа автоматически удаляет движения при отмене проведения;
- расширение добавило типизированный реквизит `Заказ`;

- одинаковый товар может встретиться в нескольких строках;
- один заказ может иметь несколько связанных расходов;
- услуги присутствуют в той же табличной части и не дают складского движения;
- существующего регистра с предметом «остаток к исполнению заказа» нет.

Для каждого утверждения укажи путь, участок и тип доказательства: `metadata`, `source`, `runtime` или `assumption`.

## 4. Формулируем бизнес-контракт

До выбора регистра согласуй поведение.

### 4.1. Два независимых состояния

```text
СостояниеЗаказа
  Открыт / ВРаботе / Выполнен / Закрыт
  изменяется пользователем и описывает жизненный цикл

СостояниеИсполнения
  НеНачато / Частично / Выполнено
  вычисляется системой по движениям
```

`СостояниеИсполнения` — фиксированный набор, поэтому в учебном решении это новое перечисление расширения. Значение не хранится вторым реквизитом заказа: форма и отчёт получают его из фактического остатка.

### 4.2. Что создаёт план

- Только проведённый заказ создаёт план исполнения.
- Каждая строка заказа увеличивает доступное к отгрузке количество.
- Одинаковые товары нескольких строк суммируются.
- Перепроведение заменяет прежний план новым.
- Непроведённый заказ — черновик; провести связанный расход по нему нельзя.

Это новое прикладное значение проведения заказа. Оно должно быть явно записано в спецификации, потому что раньше Demo83 разрешала проведение, но не использовала его для движений.

### 4.3. Что считается исполнением

- Только проведённый `РасходТовара` с заполненным `Заказом` уменьшает остаток.
- Несколько расходов по одному заказу суммируются.
- Расход без заказа продолжает работать по прежним правилам и не участвует в исполнении.
- Все строки табличной части, включая услуги, участвуют в контракте исполнения; складской остаток и исполнение заказа — разные предметы учёта.
- Товар расхода должен присутствовать в заказе.

### 4.4. Избыточная отгрузка

Проведение запрещается, если после движений хотя бы по одной комбинации `Заказ + Товар` остаток становится отрицательным.

Сообщение должно назвать:

- заказ;
- товар;
- заказанное количество;
- уже отгруженное количество;
- количество текущего расхода;
- допустимый остаток.

Проверка выполняется не по сумме документа и не по номеру строки.

### 4.5. Закрытый заказ

Новый связанный расход по заказу со значением `Закрыт` проводить нельзя. Существующие движения не удаляются автоматически. Возврат заказа в работу — отдельное явное действие пользователя.

### 4.6. Отмена и изменение

- Отмена проведения расхода возвращает остаток к исполнению.
- Перепроведение заменяет прежние движения.
- Изменить ссылку на заказ или строки проведённого расхода можно только через стандартный цикл отмены и повторного проведения.
- Распроведение заказа с существующими отгрузками запрещается либо получает отдельный согласованный маршрут. В базовом решении выбираем запрет с понятным сообщением.

## 6. Проектируем регистр

Принятое учебное решение:

```text
РегистрНакопления.AI_ИсполнениеЗаказов
Вид регистра: Остатки

Измерения:
  Заказ: ДокументСсылка.Заказ
  Товар: СправочникСсылка.Товары

Ресурсы:
  Количество: Число
```

Почему это регистр остатков:

- заказ создаёт доступное количество;
- расход его уменьшает;
- остаток имеет самостоятельный бизнес-смысл;
- отрицательный остаток означает нарушение контракта;
- отмена и перепроведение естественно отражаются движениями регистраторов.

Оба измерения имеют смысл и для прихода, и для расхода. Бизнес-правило проведения обязано отклонять движения с пустым `Заказ` или `Товар`; это не заявление о платформенном свойстве обязательности измерения. Логика и отчёты не должны читать поля регистратора через точку: нужные `Заказ` и `Товар` хранятся прямо в измерениях.

В `design.md` отдельно запиши решение об итогах:

- какие запросы читают `Остатки`;
- нужен ли режим разделения итогов;
- какой выигрыш конкурентной записи ожидается;
- какую цену это создаёт для чтения;
- почему решение нельзя называть оптимизацией без измерения.

Для учебной базы допустимо начать без разделения итогов и зафиксировать это как решение в пользу простого и быстрого чтения остатков. На УНФ этот выбор нельзя переносить без измерений.

## 7. Проектируем движения и порядок контроля

### Заказ

При проведении заказ формирует приход по каждой агрегированной паре `Заказ + Товар`.

Обычный первый приход только увеличивает остаток, но перепроведение уже проведённого заказа может заменить прежний план меньшим. Поэтому заказ тоже обязан проверить отрицательные остатки после записи нового набора: правило «приход не требует контроля» здесь неприменимо без оговорки о замене собственных прежних движений.

До реализации нужно подтвердить:

- расширение может объявить новый регистр в составе движений заимствованного документа;
- обработчик расширения не дублирует строки при перепроведении;
- отмена проведения удаляет движения нового регистра;
- запрет распроведения при наличии расходных движений реализуем без изменения типовой конфигурации.

### Расход товара

Связанный расход формирует расход по `AI_ИсполнениеЗаказов`. Несвязанный расход движений по этому регистру не создаёт.

Контролируемый регистр записывается до чтения отрицательных остатков. Проверка «сначала запросить остаток, потом записать расход» подвержена гонке: два сеанса могут увидеть один доступный остаток.

В `design.md` зафиксируй единый порядок ресурсов для проведения расхода. Канонический порядок курса: сначала комбинация склада и товара в `ТоварныеЗапасы`, затем комбинация заказа и товара в `AI_ИсполнениеЗаказов`. До записи и чтения остатков обе области должны быть явно включены в управляемую `БлокировкаДанных` с режимом `Изменение`; все пути, которым нужны оба ресурса, захватывают их только в этом порядке. Точная применимость источников блокировки к файловой Demo83 подтверждается runtime-пилотом урока 10; до него решение остаётся проектным контрактом, а не доказанным поведением.

Не добавляй внешнюю транзакцию вокруг `ОбработкаПроведения`: платформа уже выполняет проведение в своей транзакции. Внутри обработчика нельзя начинать вложенную транзакцию.

## 8. Проектируем чтение формы и отчёта

### Форма заказа

Добавляется read-only область `Исполнение`:

| Товар | Заказано | Отгружено | Осталось | Исполнение |
|---|---:|---:|---:|---|

Общий показатель:

```text
Состояние исполнения: Не начато / Частично / Выполнено
Процент исполнения: 0–100%
```

Данные рассчитываются одним серверным запросом. Запрос не выполняется отдельно для каждой строки и не читает реквизиты регистратора через точку.

Текущее заказанное количество берётся из агрегированных строк самого заказа, остаток — из регистра, а отгруженное вычисляется как `Заказано - Осталось`. Это отчёт о текущем состоянии, а не восстановление исторического плана на произвольную дату.

### Отчёт `AI_ИсполнениеЗаказов`

Минимальный отчёт показывает:

- заказ;
- покупателя;
- пользовательское состояние заказа;
- вычисляемое состояние исполнения;
- процент исполнения;
- число позиций с остатком;
- расшифровку до товара.

Отчёт не становится вторым местом расчёта. В основном маршруте общий серверный владелец возвращает таблицу значений, а СКД получает её как внешний набор данных `ИсполнениеЗаказов`. Если пилот покажет ограничение этого маршрута, допустим отдельный запрос СКД, но тогда общая формула фиксируется как контракт и проверяется одинаковыми наборами данных.

## 9. Проектируем проверку раньше реализации

Скопируй [acceptance-matrix.md](references/acceptance-matrix.md) в спецификацию и для каждой строки назначь уровень:

- `YAXUNIT` — расчёт, движения, отказ и перепроведение;
- `VANESSA` — форма, доступность и сообщение пользователю;
- `NATIVE` — метаданные, сборка, загрузка, движения в базе;
- `CONCURRENCY PILOT` — два параллельных проведения;
- `MANUAL` — только если автоматизация пока не имеет устойчивого маршрута.

Каждое требование должно получить исполняемую проверку или явный остаточный риск. Фраза «проверить всё» не является тест-планом.

Создай новый каталог изменения:

```text
openspec\changes\ai-course-order-fulfillment\
```

Сохрани первоначальную формулировку пользователя в `original-task.md`, не редактируя её задним числом. Для остальных файлов используй [spec-template.md](references/spec-template.md).

Разделение файлов:

- `spec.md` — наблюдаемое поведение и границы;
- `design.md` — регистр, движения, блокировки, запросы и альтернативы;
- `tasks.md` — последовательность маленьких проверяемых изменений;
- `original-task.md` — история запроса.

Не помещай в `spec.md` конкретные строки BSL. Требование «при двух одновременных расходах отрицательного остатка не возникает» устойчивее предполагаемой реализации блокировки.

## 11. Проводим жёсткое review спецификации

```text
Проведи read-only review изменения
openspec/changes/ai-course-order-fulfillment.

Используй $unica:register-design, $unica:document-posting,
$unica:transactions-locks и $unica:test-authoring.

Проверь:
1. разделены ли жизненный цикл заказа и исполнение;
2. соответствует ли класс регистра предмету учёта;
3. значимы ли оба измерения в обоих направлениях;
4. определены ли проведение, отмена и перепроведение обоих документов;
5. выполняется ли контроль после записи контролируемого регистра;
6. задан ли единый порядок блокировок;
7. нет ли чтения полей регистратора через точку;
8. покрыт ли каждый критерий тестом или остаточным риском;
9. какие возможности расширения требуют runtime-spike.

Ничего не изменяй. Верни BLOCKER, QUESTION и OPTIONAL отдельно.
```

Каждый `BLOCKER` либо исправляется доказательством и изменением спецификации, либо оставляет задачу в статусе `BLOCKED`.

## 12. Контролируемая ошибка: самый короткий путь

Плохое предложение:

```text
После проведения расхода получить заказ, поставить Выполнен и записать.
```

Оно не отвечает:

- была ли отгрузка частичной;
- есть ли другие расходы;
- что делать при отмене;
- кто владеет ручным `Закрыт`;
- что произойдёт при одновременном проведении;
- как восстановить данные после ошибки;
- почему запись связанного заказа безопасна внутри проведения.

Запиши, почему маленький diff имеет большой blast radius. Это должно попасть в `03-review.md` как отклонённое решение агента.

## 13. Условия готовности к реализации

Статус `READY` возможен, если:

- все факты текущего состояния имеют пути и доказательства;
- прежняя спецификация ссылки не переписана задним числом;
- два состояния разделены;
- бизнес-правила частичной, полной и запрещённой избыточной отгрузки согласованы;
- выбран и описан регистр;
- движения обоих документов определены;
- отмена и перепроведение имеют ожидаемый результат;
- порядок блокировок назван;
- форма и отчёт читают один источник истины;
- каждый критерий связан с уровнем проверки;
- runtime-вопросы расширения перечислены как гейты урока 10;
- агент не изменил исходники.

Если неизвестно, можно ли расширением безопасно добавить регистр в движения обоих документов, результат урока — корректный `BLOCKED`, а не приблизительный план реализации.

## 14. Состояние после урока

Исследование не должно менять исходники и информационную базу. Проверь:

```powershell
git status --short
git diff -- src/extensions/AI_Course_Lab
```

Допустимы только согласованные Markdown-артефакты OpenSpec и evidence. Если агент создал XML, BSL, временное расширение или запустил базу, остановись, установи точный результат действия и восстанови baseline адресно. Не удаляй неизвестные файлы общей очисткой.

## 15. Самостоятельная задача

Добавь в спецификацию сценарий изменения заказа после частичной отгрузки:

- увеличение заказанного количества;
- уменьшение не ниже уже отгруженного;
- попытка уменьшить ниже отгруженного;
- добавление нового товара;
- удаление полностью неотгруженного товара.

Для каждого определи ожидаемое поведение, движение регистра и проверку. Не оставляй решение «как получится у платформы».

## 16. Рефлексия

1. Какой факт сильнее всего изменил первоначальную задачу?

3. Что делает регистр накопления лучше запроса по документам именно в этой задаче?
4. Где возникает ответственное чтение?
5. Какой конкурентный дефект не виден в последовательном ручном тесте?
6. Какой вопрос ещё требует runtime, а не чтения XML?
