# Урок 3. Создаём отчёт с нуля вместе с агентом

> Результат: новый внешний отчёт по заказам покупателей, который показывает число заказов и сумму по покупателю за выбранный период. Ты можешь объяснить источник каждой цифры и показать проверку на заранее известных данных.

Это первый полный цикл курса: задача → исследование → короткая спецификация → ограниченное изменение → проверка → решение. Новое здесь — работа с запросом и СКД. OpenSpec-пакет для этого небольшого задания не требуется.

## Выбери контур

Используй Demo83 1.0.41.3 в отдельной восстанавливаемой учебной базе. Исследование исходников подтвердило у документа `Заказ` поля `Покупатель` и `Сумма`; перед реализацией проверь их в своей версии. Альтернатива — собственная разрешённая задача с теми же этапами и своей карточкой критериев. Для выполнения проверки в собственной базе нужен отдельный выпуск `PREPARED-COPY` из [урока безопасности](../01-safety-and-route/lesson.md). Если допущены только `OWN-SOURCES`, проектируй свой отчёт по исходникам, а полный runtime-цикл пройди на Demo83.

Для Demo83 используй **внешний отчёт** как самостоятельный артефакт. Не меняй типовую конфигурацию. До любых запусков в базе зафиксируй её путь, версию и точку восстановления. Новый отчёт проверяется по этапам: исходники/структура, нативное открытие, значения и пользовательский сценарий. Один зелёный этап не доказывает остальные.

## 1. Сформулируй задачу до агента

Пользователь спрашивает: «Сколько заказов оформил каждый покупатель за период и на какую общую сумму?» Запиши короткий контракт:

| Пункт | Решение для учебной Demo83 |
|---|---|
| Источник | Документ `Заказ`; фактические поля проверить в метаданных |
| Период | От начала выбранного дня до конца выбранного дня включительно; границы явно проверить |
| Строка отчёта | Один покупатель с числом заказов и суммой сохранённых заказов |
| Итог | Сумма строк без двойного счёта |
| Отбор | Необязательный покупатель; без отбора видны все выбранные |
| Пустой результат | Понятный пустой отчёт, а не ошибка и не старые строки |

Перед реализацией реши, включать ли помеченные на удаление заказы и какие состояния нужны пользователю. Для учебного эталона используй только непомеченные заказы; другие бизнес-правила требуют отдельного явного решения. Не позволяй агенту незаметно выбрать их за тебя.

Сохрани задачу в `Evidence/Report/01-task.md` без реальных имён и сумм. Запрос к агенту должен содержать критерии, границу файлов и требование сначала показать план.

## 2. Подготовь данные, которым доверяешь

Используй [лист контрольных данных](references/fixture-and-rubric.md). В отдельной учебной базе создай или выбери четыре заказа: два одного покупателя, один другого внутри периода и один заказ за пределами периода. Запиши ссылки и **сохранённые** значения `Сумма`; ожидаемые итоги посчитай сам до запуска отчёта. Не используй числа, придуманные агентом, как эталон.

Если интерфейс или правила Demo83 не дают подготовить такой набор без дополнительных действий, остановись и зафиксируй `BLOCKED` для fixture. Не изменяй движения, права или типовую конфигурацию только ради подгонки упражнения.

## 3. Исследуй источник и предложи план

Передай агенту карту из [урока 2](../02-first-investigation/lesson.md) и попроси на чтение:

```text
Найди метаданные Заказа и существующие отчёты Demo83 как образцы.
Подтверди поля Покупатель, Сумма, Дата и признак удаления.
Предложи минимальный внешний отчёт на СКД для задачи из 01-task.md.
Пока ничего не меняй. Назови состав артефакта и проверки,
которые отличат ошибку запроса от ошибки оформления СКД.
```

Сравни два варианта: запрос к документам и чтение из готового регистра. Для этого контракта заказы не равны продажам: регистр `Продажи` формируется другим событием. Выбери источник по вопросу пользователя, а не по наличию красивого примера в конфигурации.

## 4. Разреши одну реализацию

После проверки плана разреши агенту создать только исходники одного внешнего отчёта и необходимые для него файлы. Попроси использовать предметные операции Unica для структуры СКД и сохранить preview до записи. Не разрешай менять документы, общие модули, регистры, настройки базы или существующие отчёты.

Проверь фактический diff:

- источник данных и поля совпадают с контрактом;
- параметры периода передаются явно;
- нет соединения с табличной частью, умножающего число заказов;
- итог считается из тех же строк, что видит пользователь;
- нет встроенных клиентских данных, секретов или абсолютных путей к твоей базе;
- новые файлы относятся только к отчёту.

Структурная проверка СКД и диагностика BSL проверяют исходники. Далее понадобится нативное открытие точного собранного артефакта в учебной базе. Если сборка/открытие не выполнялись, отметь этот этап `BLOCKED`.

## 5. Проверь поведение

Сравни результат отчёта с листом контрольных данных по четырём случаям:

1. весь период: две строки и общий итог по трём заказам внутри периода;
2. отбор первого покупателя: два заказа и их сумма;
3. пустой период: нет строк и нет старого итога;
4. заказ на границе периода: он появляется ровно в том периоде, который указали.

Запиши фактические числа, скриншот результата на синтетических данных при необходимости и связь каждой строки с исходными заказами. Скриншот помогает показать вид, но не заменяет таблицу ожидаемых и фактических значений. Если получился неверный итог, сначала проверь подготовленные данные и текст запроса; не проси агента переписать всё сразу.

## 6. Прими или отклони

Заполни `Evidence/Report/04-acceptance.md`:

```markdown
# Приёмка первого отчёта
- Решение: ACCEPT / REJECT / BLOCKED
- Версии базы и артефакта:
- Что подтвердили структура и сборка:
- Ожидаемые и фактические значения четырёх случаев:
- Что осталось непроверенным:
- Состояние Git и учебной базы:
- Путь восстановления:
```

Сверь работу с [рубрикой](references/fixture-and-rubric.md). `ACCEPT` требует корректного источника, определённого результата нативного открытия и совпадения четырёх проверок. `REJECT` означает найденное нарушение контракта. `BLOCKED` означает, что обязательный этап не удалось наблюдать. В следующем уроке задача усложнится: результат нужно будет встроить в типовую УНФ через расширение.
