# Урок 7. Когда сначала нужна спецификация

> Результат: ты поручаешь агенту следующую доработку расширения через SDD и bsl-flow, а затем сверяешь реализацию с согласованными правилами, а не с впечатлением от кода.

До сих пор задачи помещались в короткий запрос: одно поле, одна команда, один файл. Теперь коллега просит: «Сделай выгрузку нескольких заказов в XML. Если один не выгрузился, остальные должны уйти». В этой фразе нет ответа на важные вопросы. Что значит «ушли» — файлы на диске или HTTP-отправка? Что делать при повторе? Как назвать файлы? Можно ли оставить часть результата после ошибки? Начинать с генерации кода рано.

Для упражнения остаёмся в учебном расширении [урока 4](../04-unf-extension/lesson.md). Здесь «выгрузка» означает **локальные файлы**, без сети. Новая команда получает список выбранных учебных заказов. Один файл — один заказ, содержимое по формату урока 4. Имя файла строится из стабильного идентификатора заказа. Существующий файл не перезаписывается. Ошибка одного заказа не останавливает остальные; итог показывает число созданных, пропущенных и ошибочных файлов. Пустой выбор не создаёт файлов. Эти правила выбраны для упражнения; для рабочей задачи их надо согласовать с владельцем процесса.

## Что здесь добавляет SDD и bsl-flow

SDD (*specification-driven development*) означает, что до реализации мы описываем наблюдаемое поведение и проверяем спорные правила. Затем код сравнивается с этой спецификацией. Для одного поля из урока 4 хватало короткого запроса. Для пакетной выгрузки уже важны выбор заказов, имена файлов, повтор и частичная ошибка: их легко реализовать по-разному и получить внешне правдоподобный результат.

[BSL Flow](https://github.com/fokusov/bsl-flow) даёт 1С-проекту навыки для исследования, спецификации, ревью, реализации и проверки. Есть два режима. В **assisted** агент применяет отдельные навыки, а последовательность шагов ведёшь ты. В **managed** навык `1c-task` передаёт задачу контроллеру: тот ведёт этапы, хранит их состояние и останавливается, когда обязательная проверка не выполнена. В этом уроке попробуем managed. Установка bsl-flow сама по себе не запускает задачу и не подключает информационную базу.

## 1. Установи bsl-flow на Windows

Этот шаг выполняется один раз на компьютере, **перед** задачей о пакетной выгрузке. Если bsl-flow уже установлен, выполни проверки схемы и навыков ниже; повторная установка не нужна. Для опубликованной версии нужны PowerShell 7, Git, Node.js, Codex CLI и OpenSpec. Проверь их в новом терминале PowerShell 7:

```powershell
pwsh --version
git --version
node --version
codex --version
openspec --version
```

Если OpenSpec отсутствует, установи версию, указанную в [актуальном `INSTALL.md` bsl-flow](https://github.com/fokusov/bsl-flow/blob/main/INSTALL.md). Для редакции, по которой написан этот урок, команда была `npm install -g @fission-ai/openspec@1.11.0`. Не устанавливай её повторно, если подходящая версия уже есть.

Склонируй [публичный репозиторий](https://github.com/fokusov/bsl-flow) в отдельную папку **вне проекта УНФ**. Если он уже склонирован, открой существующую папку и прочитай её `INSTALL.md`. Пример для нового клона:

```powershell
git clone https://github.com/fokusov/bsl-flow.git C:\AI-Course-Work\bsl-flow
Set-Location C:\AI-Course-Work\bsl-flow
Get-Content .\INSTALL.md -TotalCount 100
.\scripts\Install-BSLFlow.ps1 -WhatIf
```

Просмотри план `-WhatIf`: установщик меняет общие навыки агента, схему OpenSpec и управляемый блок глобального `AGENTS.md`, делает резервные копии. Если план соответствует `INSTALL.md` клона, выполни `.\scripts\Install-BSLFlow.ps1`. Если PowerShell блокирует запуск скриптов, в документации проекта приведено `Set-ExecutionPolicy -Scope Process Bypass` для текущего сеанса. Не копируй секреты или настройки провайдера в чат и учебный Git-проект.

После установки перезапусти Codex и проверь в терминале:

```powershell
openspec schema validate bsl-flow
Test-Path "$env:USERPROFILE\.agents\skills\1c-task\SKILL.md"
Test-Path "$env:USERPROFILE\.agents\skills\1c-init-project\SKILL.md"
```

Схема должна пройти проверку, а обе команды `Test-Path` вернуть `True`. Это подтверждает **установку файлов**, но не готовность ревьюера или тестовой базы. Для обязательного независимого ревью managed-режиму может понадобиться провайдер, настроенный по `INSTALL.md`; его ключ задают через переменную окружения или локальный файл вне Git. Если он не настроен, контроллер остановится на соответствующем этапе. YAxUnit и Vanessa для самой установки не требуются.

## 2. Подготовь учебный проект

Вернись в Codex, открой проект с разрешёнными исходниками учебной УНФ и расширения. Создай **отдельную задачу «Подготовить bsl-flow»**. Попроси проверить точный корень Git-проекта, существующие `AGENTS.md`, `bsl-flow.yaml`, `.bsl-flow/project.yaml` и `openspec/config.yaml`. Если проект ещё не инициализирован и конфликтов нет, агент применяет установленный `1c-init-project` к **этому корню**, затем показывает созданные файлы и результат проверки схемы. Для нового пустого каталога сначала нужно явно подтвердить, что он и есть корень 1С-проекта; обычную папку с курсом или папку с базами инициализировать нельзя.

После подготовки в проекте должны быть схема `bsl-flow`, конфигурация и правила проекта. Проверь `git status --short`: managed-контроллер начинает работу из чистого Git-проекта. Если изменения прошлых уроков ещё не приняты, сначала заверши их проверку и сделай локальный коммит; публиковать его для урока не нужно. Это пока не доказывает, что контроллер сможет выполнить ревью или тесты. Если установка навыка, bootstrap или обязательный провайдер не готовы, остановись на этом шаге и сверяй сообщение ошибки с `INSTALL.md` и [контрактом `1c-task`](https://github.com/fokusov/bsl-flow/blob/main/global/skills/1c-task/references/task-contract.md).

## 3. Найди границы изменения

Начни **новую задачу Codex «Пакетная XML-выгрузка» в том же проекте**. Она не наследует переписку об установке, зато видит подготовленные файлы проекта. Сначала попроси агента исследовать существующую выгрузку:

```text
Исследуй наше учебное расширение из урока 4. Найди команду выгрузки
одного заказа, её входы и побочные эффекты, форму списка заказов
и подходящую точку для команды пакетной выгрузки. Ничего не меняй.
Покажи реальные объекты и файлы, а также вопросы, без ответов
на которые нельзя формулировать задачу для bsl-flow.
```

Сверь ссылки на объекты с исходниками. Вопросы об идентичности файла, повторе и частичной ошибке должны появиться до кода. Если агент их пропустил, укажи на эти три ситуации явно.

## 4. Передай задачу в bsl-flow

Теперь у агента есть факты и правила. Отправь ему запрос как на **управляемую задачу** `1c-task`, без самостоятельного перескакивания между этапами:

```text
Создай управляемую задачу bsl-flow для учебного расширения.
Цель: пакетная локальная XML-выгрузка выбранных заказов через новую
команду, используя формат выгрузки одного заказа из урока 4.
Один заказ — один файл по стабильному идентификатору. Существующий
файл не перезаписывать; при ошибке одного заказа продолжать остальные.
Пустой выбор не создаёт файлов. Итог: создано / пропущено / ошибки
с указанием конкретных заказов. Сеть и типовую конфигурацию не менять.
Сначала подготовь спецификацию с наблюдаемыми критериями и проверь её
по маршруту проекта. Покажи мне вопрос, если правило осталось неясным.
Только после готовой спецификации запускай предусмотренные этапы
реализации и проверки. Не загружай расширение в базу.
```

Продолжай **эту же задачу Codex**: исследование и managed-прогон служат одному результату. После регистрации контроллер вернёт идентификатор задачи bsl-flow, а `Run` проведёт её через нужные этапы. Если он остановится и попросит ответ, уточни правило в той же задаче; не регистрируй вторую задачу bsl-flow ради повтора. На шаге спецификации ищи не длинный документ, а ответы на конкретные вопросы: какой заказ попадёт в выбор, что считается повтором, что происходит с уже созданными файлами после ошибки, где виден итог.

## 5. Сверь результат с четырьмя сценариями

Подготовь в учебной базе три вымышленных заказа. Для первого заранее создай файл с ожидаемым именем: он должен быть пропущен. Для второго попроси агента предусмотреть контролируемую ошибку файловой записи в тесте без изменения рабочих правил. Третий должен выгрузиться **после** этой ошибки: так проверяется продолжение обработки. Ожидаемый итог согласуй со спецификацией: один созданный файл, один пропуск, одна ошибка. Отдельно проверь пустой выбор и повтор. Если воспроизвести ошибку записи в твоём контуре нельзя, не объявляй этот сценарий пройденным.

До запуска в 1С прочитай итог контроллера: какие исходники менялись, что прошло статическую проверку, какие тесты действительно запускались и что осталось без runtime-доказательства. Сборка `.cfe`, загрузка в **учебную** базу и проверка команды — отдельные шаги. Установленный bsl-flow может подтвердить только поддерживаемый им нативный контур; успешный source-only прогон не означает, что эта команда уже работает в твоей УНФ.

SDD здесь полезен тем, что неприятные варианты поведения получают ответ **до** кода. Самый важный результат урока — совпадение реализованной команды и наблюдаемых сценариев с согласованной спецификацией. Если нужный тестовый контур пока недоступен, не выдавай исходники за проверенную пакетную выгрузку.
