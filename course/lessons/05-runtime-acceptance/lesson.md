# Урок 5. Проверяем изменение в 1С и принимаем результат

> Цель урока: провести подготовленный в уроке 4 diff через нативную загрузку и runtime-проверку, локализовать наблюдаемое влияние свойств безопасности расширения и принять либо отклонить результат на основании наблюдений, а не уверенности агента.

> Этот урок изменяет учебную информационную базу. Он начинается только после проверки точного пути, резервной копии и возможности восстановления.

## Рабочая ситуация и итоговый артефакт

Агент уже изменил исходники `AI_Course_Lab`. Статические проверки прошли, но пока неизвестно:

- примет ли платформа XML расширения;
- обновится ли конфигурация базы;
- вызовется ли обработчик заполнения;
- сохранится ли ссылка на заказ;
- правильно ли форма изменит доступность поля;
- не сломалось ли прежнее заполнение расхода.

Главный результат урока — не установленное расширение само по себе, а пакет приёмки:

```text
Evidence\Lesson-5\01-preflight.md
Evidence\Lesson-5\02-native-steps.md
Evidence\Lesson-5\03-runtime-pilot.md
Evidence\Lesson-5\04-acceptance.md
```

Последний файл содержит одно явное решение: `ACCEPT`, `REJECT` или `BLOCKED`.

## Два навыка урока

### AI-навык

Разделять действие агента и разрешение на изменение внешнего состояния; требовать прогноз до запуска; читать квитанции и журналы; локализовать слой ошибки; не разрешать повтор неизвестно завершившейся операции; принимать результат самостоятельно.

### 1С-навык

Загрузка и обновление расширения; различие конфигурации расширения и конфигурации базы данных; применимость и безопасный режим; нативная проверка; проверка заполнения по основанию, записи, проведения и событий управляемой формы.

## Основной и ускоренный маршруты

### Основной маршрут

Пройти все шаги урока, заполнить четыре файла свидетельств и вручную выполнить семь runtime-сценариев.

### Ускоренный маршрут для опытного 1С-разработчика

Можно не повторять объяснение интерфейса Конфигуратора и различий между конфигурациями, если ты можешь своими словами объяснить:

1. почему загрузка XML ещё не означает обновление базы;
2. почему exit code 0 ещё не доказывает бизнес-поведение;
3. почему безопасный режим нельзя отключать автоматически;
4. чем Git-откат отличается от восстановления файловой базы.

Preflight, резервная копия, семь сценариев и решение о приёмке не пропускаются.

## Сколько времени понадобится

- самостоятельно: 2,5–3,5 часа;
- с преподавателем: около 160 минут;
- ускоренный маршрут сокращает объяснения интерфейса, но не runtime-сценарии и не фиксацию evidence.

## Что понадобится

- завершённый [урок 4](../04-controlled-change/lesson.md);
- чистое и известное состояние до начала runtime-операций;
- непринятый diff только в `src\extensions\AI_Course_Lab`;
- согласованная спецификация `openspec/changes/ai-course-order-link/spec.md`;
- файловая учебная база Demo83 со статусом `READY`;
- пользователь `Администратор` учебной базы;
- платформа поддерживаемой версии;
- возможность закрыть все сеансы и восстановить базу;
- отдельный каталог `Evidence\Lesson-5`.

Если база, пользователь, версия платформы или состав diff неизвестны, урок имеет статус `BLOCKED`.

## Единый цикл в этом уроке

```text
RESEARCH
проверить diff, базу, процессы и точки восстановления
        ↓
SPEC
сверить семь сценариев со спецификацией
        ↓
IMPLEMENT
загрузить уже подготовленное расширение без нового кода
        ↓
VERIFY
проверить нативные журналы и поведение в 1С
        ↓
ACCEPT / REJECT
зафиксировать решение и состояние базы
```

На стадии `IMPLEMENT` агент не продолжает «улучшать» исходники. Здесь реализация означает только контролируемое применение уже проверенного изменения к учебной базе.

## Итоговая схема урока

```text
проверенный diff урока 4
  → прогноз ожидаемого результата
  → preflight и backup
  → план нативных действий без запуска
  → однократная загрузка XML
  → проверка фактического состояния
  → однократное обновление БД
  → нативная проверка и CFE
  → первый runtime-сценарий
  → диагностика безопасного режима при отсутствии эффекта
  → семь сценариев
  → ACCEPT / REJECT / BLOCKED
```

## Часть 1. Сначала предсказываем результат

До запуска 1С заполни:

```text
C:\AI-Course-Work\Evidence\Lesson-5\01-preflight.md
```

Начни с прогноза:

```markdown
# Preflight урока 5

## Ожидаем после загрузки

- В расширении появится реквизит РасходТовара.Заказ.
- Расход на основании заказа получит ссылку после типового заполнения.
- Ручной расход сможет остаться без заказа.
- Поле будет редактироваться до проведения.
- После проведения поле станет только для чтения.
- Основная конфигурация и движения документов не изменятся.

## Если эффекта нет, проверяем по порядку

1. загрузилась ли конфигурация расширения;
2. обновлена ли конфигурация базы данных;
3. активно и применимо ли расширение;
4. не ограничивает ли выполнение безопасный режим;
5. вызван ли нужный обработчик;
6. только затем — есть ли ошибка в BSL или форме.
```

Этот прогноз нужен, чтобы после ошибки не принимать первое объяснение агента за диагноз.

## Часть 2. Выполняем preflight

### 2.1. Проверяем Git и скоуп

Из корня `Demo83-Sources` выполни:

```powershell
git status --short
git diff --stat
git diff --check
git diff --exit-code -- src/configuration
```

Сохрани вывод в `01-preflight.md`.

Продолжать можно, если:

- нет неизвестных изменений;
- изменено только учебное расширение и согласованные файлы свидетельств;
- основная конфигурация не имеет diff;
- полный diff уже прочитан в уроке 4.

### 2.2. Проверяем точную базу

Запиши:

```text
Имя базы: AI Course — Demo83
Путь: C:\AI-Course-Work\Demo83-Base
Пользователь: Администратор
Версия платформы:
Версия Demo83:
Текущий Git-коммит:
```

Не выбирай базу только по похожему имени в стартовом окне. Сверь абсолютный путь.

### 2.3. Закрываем сеансы и создаём точку восстановления

Перед загрузкой расширения:

1. закрой пользовательские сеансы и Конфигуратор;
2. убедись, что файловая база не занята процессами 1С;
3. создай новую резервную копию или подтверди неизменность рабочего baseline;
4. запиши путь, размер, время и SHA-256 копии;
5. не перезаписывай прежнюю копию с тем же именем.

Наличие `.dt` или копии `1Cv8.1CD` не доказывает восстановимость само по себе. В уроке 2 восстановление уже должно быть выполнено фактически.

## Часть 3. Получаем от агента план нативных действий

Дай Codex задачу:

```text
Подготовь план runtime-проверки изменения `ai-course-order-link`.

Сейчас ничего не запускай и не изменяй.

Целевая база:
C:\AI-Course-Work\Demo83-Base

Исходники расширения:
C:\AI-Course-Work\Demo83-Sources\src\extensions\AI_Course_Lab

Нужно перечислить:
1. read-only preflight;
2. точную операцию загрузки исходников расширения;
3. отдельное обновление конфигурации базы данных;
4. нативную проверку;
5. выгрузку CFE и его SHA-256;
6. проверку фактического состояния после каждого шага;
7. семь runtime/UI-сценариев из спецификации;
8. путь восстановления.

Для каждого шага укажи:
- что изменяется;
- ожидаемый результат;
- свидетельство;
- стоп-условие.

Не предлагай повторять загрузку или обновление автоматически после ошибки.
После плана остановись.
```

### Проверяем план

Отклони план, если агент:

- не назвал точную базу;
- смешал загрузку исходников и обновление БД в непрозрачный шаг;
- не предусмотрел проверку после операции;
- предлагает отключить защитные свойства заранее;
- считает запуск клиента доказательством всех требований;
- собирается повторять команду после неопределённого результата;
- не сохранил путь восстановления.

План сохраняется в:

```text
Evidence\Lesson-5\02-native-steps.md
```

## Часть 4. Загружаем расширение по одному шагу

В курсе допустимы два поддерживаемых маршрута:

- штатные команды Конфигуратора;
- команды Unica/v8-runner, для которых сначала получен preview точных аргументов, а каждый applied-шаг имеет отдельную квитанцию. Если такая команда в установленной версии недоступна, используй Конфигуратор.

Нельзя использовать неизвестный скрипт только потому, что его предложил агент.

### 4.1. Загрузка конфигурации расширения

Выполни только загрузку XML в расширение `AI_Course_Lab`.

До запуска произнеси прогноз:

> Платформа должна принять исходники расширения. Прикладные таблицы базы ещё не обязаны измениться, а пользовательский сценарий ещё не проверен.

После завершения зафиксируй:

- время;
- точную команду или путь в интерфейсе;
- exit code либо сообщение Конфигуратора;
- журнал;
- появилось ли расширение в списке;
- активно ли оно и применимо ли к текущей конфигурации.

Если результат команды неизвестен, остановись и исследуй фактическое состояние. Не запускай загрузку повторно «для уверенности».

### 4.2. Обновление конфигурации базы данных

Только после успешной загрузки выполни обновление конфигурации базы данных расширения.

Ожидаемый результат:

```text
изменён объект Документ.РасходТовара
```

Если платформа предлагает несвязанные реструктуризации или изменения основной конфигурации, откажись и поставь `BLOCKED`.

### 4.3. Нативная проверка и CFE

Под «нативной проверкой» здесь понимается проверка конфигурации расширения средствами Конфигуратора 1С, а не только XML-валидация или BSL-диагностика агента.

После обновления:

1. выполни нативную проверку расширения;
2. сохрани полный журнал, а не только последнюю строку;
3. выгрузи `AI_Course_Lab.cfe`;
4. запиши размер и SHA-256 артефакта.

В Demo83 общая проверка может вернуть диагностические сообщения существующих объектов основной конфигурации. Раздели результаты:

- диагностики изменённого расширения;
- ранее существовавшие диагностики Demo83;
- сообщения, происхождение которых не удалось установить.

Нельзя объявить общий `PASS`, если команда завершилась ненулевым кодом. Но также нельзя приписывать расширению чужую ошибку без связи с его объектами.

## Часть 5. Первый запуск и контролируемая ошибка

Открой Demo83 в пользовательском режиме и выполни только первый сценарий:

1. открой существующий заказ;
2. создай на его основании расход товара;
3. проверь наличие и заполнение поля `Заказ`;
4. пока не записывай другие документы для диагностики.

### Если всё сработало

Запиши результат и переходи к семи сценариям.

### Если поле есть, но обработчик не сработал

Не проси агента немедленно переписать код. Используй порядок из прогноза:

1. подтверждено ли обновление БД;
2. активно ли расширение;
3. применимо ли оно;
4. включён ли безопасный режим;
5. есть ли в журнале ошибка исполнения;
6. совпадает ли фактическое основание с ожидаемым типом.

В авторском пилоте расширение загрузилось и обновило базу без ошибки; ожидаемый эффект появился после снятия безопасного режима. Это подтверждённая последовательность наблюдений данного стенда, но не доказательство общего правила «безопасный режим отключает перехватчики». Перед выводом проверь активность, применимость, обновление базы, защиту от опасных действий и журнал. Если причинный механизм не локализован, формулируй результат как условие среды и оставляй `BLOCKED` для обобщения.

## Часть 6. Принимаем решение о безопасном режиме

Безопасный режим ограничивает возможности кода расширения. Его нельзя отключать как универсальный способ исправления любой ошибки.

Перед изменением свойства ответь письменно:

- это именно отдельная учебная Demo83?
- есть ли подтверждённая точка восстановления?
- проверен ли источник CFE или исходников?
- прочитан ли diff?
- отсутствуют ли внешние компоненты и сетевые действия вне задачи?
- относится ли решение только к `AI_Course_Lab`?

Если хотя бы один ответ неизвестен, статус `BLOCKED`.

Если все ответы подтверждены, в учебной базе допускается снять безопасный режим только у проверенного `AI_Course_Lab`, перезапустить пользовательский сеанс и повторить **первый** сценарий один раз.

В рабочей базе, клиентской копии или у стороннего расширения это решение требует отдельной политики и не разрешается данным уроком.

### Что должно понять упражнение

```text
нет эффекта
  ≠ код обязательно неверен
  ≠ нужно попросить агента написать другой код

нет эффекта
  → локализуй слой: загрузка / обновление / применимость / безопасность / runtime
```

Заполняй таблицу в:

Для каждого сценария используй отдельный заранее выбранный документ или запиши точные ссылки/номера. Не заменяй фактический результат фразой «визуально всё нормально».

### Стоп-условия

- платформа показывает ошибку исполнения;
- типовое заполнение изменилось или продублировалось;
- проведение изменило неожиданные движения;
- ссылка пропала после записи;
- поле можно менять в проведённом документе;
- для продолжения требуется неизвестное изменение базы;
- результат записи неизвестен.

При стоп-сигнале сохрани состояние и журнал. Не продолжай оставшиеся записи только ради заполнения таблицы.

## Часть 8. Просим агента проанализировать свидетельства

После пилота можно дать Codex журналы и заполненную таблицу:

```text
Проанализируй пакет проверки урока 5.

Ничего не изменяй и не запускай.

Для каждого требования спецификации укажи:
- свидетельство;
- PASS, FAIL или BLOCKED;
- ограничение доказательства.

Отдельно раздели:
- статическую валидацию;
- нативную загрузку и обновление;
- диагностики основной Demo83;
- ручные runtime/UI-наблюдения;
- оставшиеся непроверенные свойства.

Предложи решение ACCEPT, REJECT или BLOCKED, но не принимай его за меня.
```

Ученик проверяет матрицу агента. Красивый отчёт не должен превращать ручной пилот в автоматизированную регрессию или ненулевой `/CheckConfig` в общий PASS.

Создай:

```text

```

Шаблон:

```markdown
# Решение по ai-course-order-link

## Решение

ACCEPT / REJECT / BLOCKED

## Что подтверждено

## Что не подтверждено

## Найденные отклонения и условия среды

## Почему выбран этот статус

## Состояние Git

## Состояние учебной базы

## Путь восстановления

## Следующий безопасный шаг
```

### Когда допустим `ACCEPT`

- diff соответствует спецификации;
- основная конфигурация не изменена;
- загрузка и обновление завершились определённо;
- все семь сценариев имеют `PASS`;
- нюанс безопасного режима записан как условие среды;
- ограничения ручного пилота названы честно;
- путь восстановления сохранён.

### Когда нужен `REJECT`

Требование нарушено, причина понятна, и текущую реализацию нельзя принимать. Сохрани diff и свидетельства, затем верни задачу агенту с конкретным несоответствием.

### Когда нужен `BLOCKED`

Критичное свойство осталось неизвестным: неопределённый результат операции, неподтверждённая база, потерянный baseline, неразделимая ошибка платформы или невозможность выполнить обязательный сценарий.

## Часть 10. Фиксируем или восстанавливаем состояние

### При `ACCEPT`

1. ещё раз проверь `git status` и diff основной конфигурации;
2. зафиксируй принятые исходники понятным коммитом;
3. не добавляй в Git базу, `.dt`, CFE, журналы с локальными путями или учётные данные;
4. создай новую именованную точку восстановления принятого состояния базы;
5. не удаляй предыдущий baseline до проверки новой точки.

### При `REJECT` или `BLOCKED`

1. сохрани текущую базу отдельно, если она нужна для расследования;
2. закрой все сеансы;
3. восстанови проверенный baseline;
4. проверь версию, состав расширений и контрольный объект;
5. не считай возврат Git восстановлением базы.

## Самостоятельная задача

Составь короткую диагностическую карточку для нового случая:

> Расширение загрузилось, форма открывается, но поле остаётся редактируемым после проведения.

Не предлагай исправление кода. Запиши:

1. пять возможных слоёв причины;
2. порядок read-only проверок;
3. какое наблюдение опровергает каждую гипотезу;
4. в какой момент агенту можно разрешить изменение исходников;
5. какое свидетельство потребуется после исправления.

Артефакт:

```text
Evidence\Lesson-5\05-diagnostic-card.md
```

## Критерии завершения урока

Урок завершён, если:

- записан прогноз до запуска;
- проверены Git, точная база и backup;
- нативные шаги выполнялись раздельно и не повторялись вслепую;
- журналы интерпретированы по границам доказательства;
- безопасный режим разобран как осознанное решение, а не магическая кнопка;
- выполнены семь сценариев или зафиксирован честный стоп;
- создана диагностическая карточка;
- человек принял решение `ACCEPT`, `REJECT` или `BLOCKED`;
- состояние Git и базы после решения известно.

## Рефлексия

Ответь письменно:

1. Где агент сэкономил время?
2. Где проверка агента добавила работу?
3. Какой результат нельзя было получить только чтением исходников?
4. Почему первый неработающий сценарий не потребовал немедленно переписать код?
5. Какое правило стоит сохранить для следующей задачи?

После этого урока в проектное правило можно добавить первый runtime-гейт:

> Перед принятием изменения формы или объектного обработчика отделять статику, загрузку, обновление БД и пользовательский сценарий; не повторять неизвестно завершившуюся операцию.

Так `AGENTS.md` растёт из пережитой ошибки, а не из заранее скопированного списка запретов.
